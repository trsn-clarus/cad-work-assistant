# PDF Quantity + Verification Report (Milestone 10)

## 1. 목표

Excel 수량산출서(Milestone 9)가 "작업 가능한 데이터 문서"라면, PDF는 제출·보고·검토·공유·보관·출력을
위한 **고정된 결과물**이다. 저장된 QuantityRecord(+최신 검산 결과+검토 상태)를 사람이 읽고 검토할 수
있는 하나의 문서로 만든다 - Excel 화면을 그대로 PDF로 복제하지 않는다.

## 2. 라이브러리 선택 — PDFsharp-MigraDoc

| 후보 | 제외 이유 |
|---|---|
| QuestPDF | 실제 nuget.org 페이지로 라이선스를 직접 확인한 결과, 연매출 $1M 미만 조직에만 무료인 Community License 조건이 있다 - 배포 대상 회사 규모를 알 수 없는 이 제품에 위험하다고 판단했다 |
| Chromium/Playwright/wkhtmltopdf로 HTML→PDF | 외부 프로세스/브라우저 런타임 의존성이 늘어난다 - 이 앱은 offline local desktop 도구다(§97-100) |
| Microsoft Word Interop | Word 설치 필요, COM lifetime 문제 - Excel의 Interop 배제 이유(§4)와 동일 |
| **PDFsharp-MigraDoc 6.2.4**(채택) | 공식 PDFsharp-Team 패키지, nuget.org로 직접 확인한 결과 조건 없는 순수 MIT. net8.0 정식 지원. MigraDoc의 Word-processor 스타일 문서 모델(Section/Paragraph/Table + 자동 페이지 나눔)이 이 보고서가 필요로 하는 "자연스러운 페이지 확장"에 잘 맞는다 |

`CADWorkAssistant.Documents`만 PDFsharp-MigraDoc을 참조한다 - `Core`와 `CADWorkAssistant.AutoCAD`는
이 패키지를 전혀 모른다(§41-43).

## 4. 공통 Document Model — Milestone 9 모델의 일반화

Milestone 9의 `Excel.QuantityWorkbookModel`/`QuantityWorkbookModelBuilder`/`ExcelExportScope`를
`Documents.Reports` 네임스페이스로 옮기고 `QuantityReportModel`/`QuantityReportRow`/
`QuantityReportModelBuilder`/`QuantityExportScope`로 이름을 일반화했다 - Excel 전용 이름
("Workbook")이 PDF에는 맞지 않았기 때문이다. `IQuantityReportOptions`(Scope/IncludeReviewNotes/
IncludeSourceDrawing만) 인터페이스를 새로 두어 `ExcelExportOptions`/`PdfExportOptions`가 공유하게
했다 - Excel의 시트 구성 옵션(IncludeCalculationBasis 등)과 PDF의 Section 구성 옵션은 렌더러마다
의미가 달라 억지로 합치지 않았다.

Excel과 PDF는 **같은 `QuantityReportModel` 인스턴스**(또는 같은 조회 결과로 만든 동일한 모델)를
그대로 소비하므로, 같은 Project+Scope라면 record 순서/필터링 결과가 항상 일치한다 - 이 보장은
`CrossFormatConsistencyTests`(Documents.Tests)로 실제 두 출력 파일을 만들어 검증했다(§14).

## 5. 보고서 구조

```text
1. 표지 / 프로젝트 요약   - 제목, 프로젝트 정보(프로젝트/현장/발주처/설명/작성일), 수량 요약,
                          주의 문구(Error/Review 항목 존재 시), 수량 요약 표
2. 항목별 산출근거        - 각 QuantityRecord를 한 블록으로: 구분/최종 수량/원본값/측정방법/
                          원본 도면/CAD 객체 수/산출식/검산 결과(글리프+세부 Check)/검토 상태+메모
```

Excel의 4-시트 구조(수량산출서/산출근거/검산내역/프로젝트정보)와 달리, PDF는 "요약 표"와 "항목별
상세"만으로 구성한다 - 검산/검토는 항목별 상세 블록 안에 함께 표시한다(별도 섹션으로 분리하지
않는다). 사람이 한 항목을 처음부터 끝까지 순서대로 읽을 수 있게 하기 위해서다.

## 6. Export Scope / 옵션

Excel과 동일한 `QuantityExportScope`(All/VerifiedOnly), 필터링은 항상 `QuantityReviewStatus` 기준
- 자동 `VerificationSeverity`로 걸러내지 않는다. `PdfExportOptions`는
`IncludeCalculationDetails`/`IncludeVerification`/`IncludeReviewNotes`/`IncludeSourceDrawing`을
갖는다(Excel의 시트 on/off와 대응하지만 PDF에서는 "항목 블록 안의 필드 on/off"로 동작한다).
`VerifiedOnly`일 때 표지 제목이 "검토 완료 수량 보고서"로 바뀐다 - 파일명 규칙은 그대로다.

## 7. 정밀도

Excel과 동일하게 `Core.Models.QuantityTypeDisplay.DecimalPlaces`가 유일한 소스다(Length 3/Area
2/VerticalArea 3/Parapet 3). 항목별 상세에는 산출근거 시트와 같은 원본값(3자리 고정, mm 등 원본
단위)도 함께 보여준다.

## 8. 한글 폰트 — 실제로 겪은 문제와 해결

PDFsharp 6.x는 .NET 8(비-GDI 빌드)에서 폰트를 전혀 모른다 - `GlobalFontSettings.FontResolver`를
등록하지 않고 렌더링을 시도하면 즉시 `InvalidOperationException("No appropriate font found")`을
던진다(실제로 빌드해서 실행해봐야 드러난 문제, 컴파일은 문제없었다). 이 앱은 애초에 Windows 전용
설치형 프로그램(WPF)이므로, Windows가 Vista부터 기본 제공해온 한글 UI 폰트 **맑은 고딕**
(`%WINDIR%\Fonts\malgun.ttf`/`malgunbd.ttf`)을 실행 시점에 직접 읽어 PDF에 임베드하는
`WindowsKoreanFontResolver`(`Documents.Pdf`, `internal`)를 구현했다. 폰트 파일 자체를 설치
프로그램에 복사/재배포하지 않는다 - 사용자의 Windows 설치본에 이미 있는 폰트를 그때그때 읽어서
PDF 안에 필요한 글리프만 내장할 뿐이다.

### 실제로 발견한 글리프 렌더링 버그

Simulation Mode 실제 UI 검증 중 생성된 PDF를 육안으로 확인하다가, 검산 결과 "Pass"를 나타내는
✓(U+2713 CHECK MARK) 글리프가 **빈 사각형(tofu)** 으로 깨지는 것을 발견했다 - 맑은 고딕 폰트에 이
Dingbats 블록 글리프가 없기 때문이다(!(Review)/×(Error)/—(없음)는 이 폰트에 이미 있어 문제없었다).
여러 후보 문자를 실제로 렌더링해 비교한 결과 ○(U+25CB WHITE CIRCLE)는 정상 렌더링되는 것을
확인했고, 한국 문서에서 흔한 ○/× 표기와도 자연스럽게 어울려 PDF 전용으로 ✓ → ○ 치환
(`QuantityPdfBuilder.ToPdfSafeGlyph`)을 적용했다. Core나 Excel은 건드리지 않았다 - Excel 뷰어는
시스템 폰트로 자동 대체해 이미 정상 표시된다. 텍스트 라벨("검산 완료" 등)은 Excel/PDF 둘 다 완전히
동일하다 - 글리프만 렌더러별로 다르다.

## 9. 페이지 레이아웃

- A4 Portrait, 여백 상단 2cm/하단 1.6cm/좌우 2cm
- Header: "{프로젝트명} · 수량 산출 및 검산 보고서"(모든 페이지 반복)
- Footer: "Generated by CAD Work Assistant · TRSN CLARUS" + "Page N / M"(MigraDoc의
  `AddPageField()`/`AddNumPagesField()`)
- 항목별 상세 섹션은 표지/요약과 분리해 새 페이지에서 시작(`Format.PageBreakBefore`)
- 각 항목 블록 내부 줄들은 `KeepWithNext`로 서로 붙여 페이지 중간에서 어색하게 끊기지 않도록
  최대한 유도한다(MigraDoc에 완벽한 "블록 전체를 항상 안 끊기게" 기능은 없다 - §61이 요구하는
  "가능한 layout control 활용" 수준으로 구현했다)
- 색상은 제목/헤더 배경 정도로만 제한(Accent `#1D6F8F`, 헤더 배경 `#EEF2F5`, 테두리 `#CAD3DC`) -
  흑백 출력에서도 텍스트 라벨로 상태를 구분할 수 있다

## 10. 원자적 저장

Excel과 완전히 같은 원칙(`QuantityWorkbookBuilder.SaveAtomically`와 동일 구조):

1. 대상 폴더에 임시 파일(`~cwa_{guid}.pdf`)로 저장
2. `PdfSharp.Pdf.IO.PdfReader.Open(tempPath, PdfDocumentOpenMode.Import)`로 다시 열어 최소 구조
   (페이지 존재)를 검증(`PdfDocumentOpenMode.InformationOnly`는 이 버전에서 이미 deprecated라
   `Import`를 쓴다 - 실제 컴파일 경고로 확인)
3. 검증을 통과했을 때만 `File.Move(..., overwrite: true)`로 원래 경로에 원자적 교체
4. 실패하면 임시 파일을 최선의 노력으로 삭제하고 원래 경로는 건드리지 않는다

`PdfDocument.PageCount`는 **`Save()` 이전에만** 읽을 수 있다 - Save 이후 PdfSharp이 문서를
read-only로 잠그고 `PageCount` 접근 자체가 `InvalidOperationException`을 던진다(실제로 겪은
문제). `QuantityPdfBuilder.BuildAndSave`는 렌더링 직후, Save 이전에 PageCount를 캡처해
`PdfExportResult.PageCount`로 반환한다.

## 11. 보안

Excel의 수식 주입 방지와 대응되는 개념은 PDF에는 없다(PDF는 셀 기반 수식 언어가 없다) - 대신
사용자 입력 문자열을 MigraDoc의 일반 텍스트 API(`Paragraph.AddText`)로만 쓰고, 어떤 마크업/명령
해석기도 거치지 않는다(§96-100, HTML-to-PDF/Chromium을 쓰지 않은 이유이기도 하다 - HTML 렌더러를
거쳤다면 사용자 입력이 스크립트로 해석될 위험이 생겼을 것이다). 원본 DWG는 파일명만(전체 경로
없음), Object Handle 전체 목록은 노출하지 않고 개수만 보여준다(§29-30).

## 12. Export 이력

`ExportRecord.ExportType`에 `PdfQuantityReport` 상수를 추가했다(Migration 불필요 - `ExportType`은
이미 TEXT 컬럼이라 새 문자열 값 하나 추가에 스키마 변경이 필요 없다). `IProjectContextService.
AddPdfExportRecordAsync`가 `AddExcelExportRecordAsync`(Milestone 9)와 완전히 같은 패턴으로
ExportRecord+ActivityRecord("수량 산출근거 PDF 저장")를 한 트랜잭션에 저장하고 Dashboard Activity
Log에 즉시 반영한다.

## 14. Cross-format Consistency

`CrossFormatConsistencyTests`(Documents.Tests)가 같은 fixture(뒤섞인 CreatedAt 순서의 레코드
3건)를 Excel과 PDF 양쪽으로 실제로 생성해서 확인한다:

- Record count 동일
- 항목 순서 동일(CreatedAt 오름차순 - Excel 셀 순서와 PDF 텍스트 등장 순서를 각각의 방식으로 추출해
  비교)
- 표시 수량 텍스트/값 동일
- 검산 텍스트 라벨 동일("검산 완료" 등 - 글리프는 §8에서 설명한 이유로 렌더러마다 다름을 의도적으로
  허용)
- 검토 상태 텍스트 동일

## 15. 이번 범위에서 의도적으로 하지 않은 것

- **PDF 암호화/디지털 서명** - 향후 보안 요구가 생기면 별도 기능
- **Draft Watermark** - 미검토 포함 보고서에 대한 워터마크는 향후 후보
- **Technical Appendix(전체 Object Handle 목록)** - 첫 버전은 업무 보고서 가독성 우선
- **PDF Export scope 세분화(선택 항목만/필터 결과만)** - Excel과 동일하게 범위 밖
- **Cancellation(대형 PDF 생성 취소)** - 실측한 생성 시간이 짧아 첫 버전에서는 구현하지 않음
- **앱 내부 PDF Viewer** - "파일 열기"는 OS Shell(기본 연결 프로그램)에 위임한다
